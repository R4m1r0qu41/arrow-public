## Executive Summary

The v1.5.1 Ethereum provenance and settlement flow passed the local pre-merge verification suite.

The tested path now verifies a signed transport envelope before the consumer can reduce or settle the event. The consumer re-checks the `arrow-canonical-json-v0` canonical bytes, Ed25519 signature, signer DID equality with `sender_id`, and a fail-closed sender allow-list. The end-to-end binary smoke test confirmed the intended trust boundary:

1. The origin adapter observed a finalized Ethereum transaction on chain A.
2. The origin adapter minted an Arrow event, signed the transport envelope, wrote it to disk with `--out`, and posted it to the signed Arrow node.
3. The node accepted the signed envelope.
4. The consumer rejected the same envelope when the allow-list was wrong.
5. The consumer accepted the same envelope when the allow-list was correct, reduced it to `ApprovedForSettlement`, and settled exactly 1 ETH on chain B.

## What This Proves

### Signature Re-Verification

The consumer does not rely on a prior node decision. It re-checks the signed envelope using:

- `arrow_transport::canonical::envelope_canonical_bytes`
- `arrow-canonical-json-v0`
- `envelope-minus-signature-and-signing`
- Ed25519 via `arrow_identity::verify::verify_signature`

This matches the node's signature verification path for the current `did:key` flow.

### Provenance Gate Before Settlement

`verify_and_consume` performs:

```text
verify envelope provenance -> validate Arrow event -> reduce event log -> settle if permitted
```

An envelope that fails provenance does not reach reduction or settlement.

### Fail-Closed Trust Model

The allow-list is fail-closed. If no sender is configured, or the sender is not in the allow-list, the consumer refuses to trust the envelope.

### Event-Bound Settlement

The settlement recipient and amount come from the observed event metadata:

```text
metadata.to
metadata.value_wei
```

The operator supplies only:

- Chain-B RPC endpoint.
- Funding account.
- Trusted sender allow-list.

This protects against the earlier CLI-driven settlement risk.

### End-to-End Binary Validity

The proof was not only library-level. The actual binaries exercised the flow:

```text
arrow-origin-eth -> arrow-node -> arrow-consume-eth -> chain B settlement
```

## Items To Review Or Reinforce

### 1. Require `--allow` At The CLI Layer

Current behavior is safe because an omitted allow-list fails at runtime with:

```text
no allowed senders configured; refusing to trust any provenance
```

Suggested reinforcement: mark `--allow` as required in Clap, or add a clearer CLI-specific error before building `ProvenancePolicy`.

Reason: fail-closed runtime behavior is correct, but a required CLI flag gives faster operator feedback.

### 2. Add Consumer DID-Method Policy If Needed

The consumer currently verifies through `MultiResolver::default_config()`, which covers the supported DID methods. The node also has explicit `allowed_did_methods`.

Suggested review: decide whether `ProvenancePolicy` should include `allowed_did_methods`, mirroring the node config exactly.

Reason: the current `did:key` path is compatible, but explicit method policy may be useful once `did:web` or other methods are enabled in production.

### 3. Share Signature Verification Logic

The consumer intentionally mirrors `arrow-node` signature verification rather than depending on the node crate.

Suggested reinforcement: consider moving the common verification routine into a shared library crate when the API stabilizes.

Reason: this reduces drift risk between node and consumer as canonicalization, DID methods, or signature algorithms evolve.

### 4. Promote Settlement Intent Out Of Free-Form Metadata

The settlement target currently rides on:

```text
event.metadata.to
event.metadata.value_wei
```

Suggested fix: define a first-class validated settlement intent field or typed metadata schema for EVM settlement events.

Reason: metadata is signed and validated indirectly, but the intent itself is still structurally free-form. A typed settlement-intent schema would make this boundary stronger.

### 5. Add Replay Protection For Consumer Envelope Ingestion

The node has replay protection. The consumer re-verifies signature and allow-list, but the current consumer path should be reviewed for repeated envelope processing semantics.

Suggested reinforcement: add consumer-side replay detection keyed by envelope ID, nonce, sender, and/or event lifecycle depending on desired settlement idempotency.

Reason: settlement systems should be idempotent even if the same signed envelope is submitted directly to the consumer more than once.

### 6. Persist Or Externalize Consumer Allow-List Configuration

The binary currently accepts repeatable `--allow` flags.

Suggested reinforcement: add a config file path for production operator policy, similar in spirit to the node config.

Reason: command-line allow-lists are good for tests and demos, but production needs auditable, versioned policy configuration.

### 7. Harden Key Handling Beyond Dev Fixtures

The tested flow uses deterministic dev/test key files containing raw private keys.

Suggested fix: keep this path explicitly dev-only and plan production signing through a wallet, KMS, HSM, or other protected signer.

Reason: raw private key JSON is acceptable for local integration tests but not for production provenance.

### 8. Run CI With Foundry For Live Ethereum Tests

The Foundry-backed tests passed locally when run with `--ignored`.

Suggested reinforcement: add a CI job that installs Foundry and runs:

```text
cargo test -p arrow-origin-eth --test live_anvil -- --ignored
cargo test -p arrow-consume-eth --test a_to_b -- --ignored
```

Reason: these tests prove the Ethereum adapter and settlement loop against real local JSON-RPC behavior, not only mocked/unit behavior.

### 9. Use Non-Default Ports Or Random Ports In Binary Smoke Scripts

The manual smoke used:

```text
18545
18546
8080
```

Suggested reinforcement: if this becomes a scripted smoke test, allocate free ports dynamically.

Reason: fixed ports are fine for one local run but can collide with developer services or parallel CI.

### 10. Clarify Receiver Semantics For Consumer-Written Envelopes

The origin adapter can write a signed envelope using `--out` and also post it to the node with a receiver DID. The consumer verifies sender provenance and payload signature but does not currently appear to enforce that the envelope receiver is the consumer.

Suggested review: decide whether the consumer should require `receiver_id` to include its own configured DID.

Reason: sender provenance proves who signed the envelope; receiver binding proves the envelope was intended for this consumer.
